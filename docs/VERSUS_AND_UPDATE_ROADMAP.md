# 漢字 de クラッシュキーボード — 更新・対戦化方針

最終更新: 2026-07-27  
対象バージョン: v0.3.0 以降

## 1. 企画の中心

本作は「難読漢字を素早く答えるだけのゲーム」ではない。

> 3語から読める語を選び、壊れそうなキーボードを管理しながら得点を伸ばす、漢字タイピング・サバイバルパズル。

中心となる判断は次の4点。

1. どの漢字なら読めるか
2. どのローマ字表記で打つか
3. どのキーを摩耗させ、どのキーを回復させるか
4. 今すぐ入力するか、復活を待つか

`si`と`shi`のような入力差は、短縮入力と長文ボーナス、使用キー数と破損リスクの選択として扱う。タイピング速度だけで勝敗が決まらないことを守る。

## 2. 守るべき設計原則

### 2.1 運は問題を作り、結果を勝手に変えない

語句の抽選にはランダム性を使う。ただし、正しい入力が確率で失敗する仕組みは入れない。敗因が「読めなかった」「入力を誤った」「キー管理を誤った」と理解できる状態を保つ。

### 2.2 失敗は次の改善へつながる

ゲームオーバーやタイムアップ時には、その時点の3語のひらがな読みとローマ字例を表示する。プレイヤーが次回は答えられる状態を作る。

### 2.3 操作制限を攻略法として認める

破損キーの10秒復活は全モード共通とし、待機も正当な戦術とする。10語モードでは待機時間がクリアタイムへ反映されるため、速度と安全性の交換関係が成立する。

### 2.4 対人攻撃を中核にしない

相手のキーを壊す、お邪魔語句を送る、HPを奪うなどの妨害機能は原則として追加しない。同一条件を各自が処理し、最終結果を比較する「並走型対戦」を基本とする。

### 2.5 プレイヤー向け文章と開発仕様を分ける

UIの説明文には、依頼文、内部実装、開発者間の検討事項をそのまま載せない。短く、操作と感情が伝わるプレイヤー向け文章へ編集する。

## 3. 現在のモード

### ソロ・30秒

- 30秒間の最終スコアを競う
- ミス回数の上限なし
- タイムアップ時に表示中の3語の読みを開示

### ソロ・10語

- 10語クリア時のスコアとクリアタイムを競う
- 5ハート制。5回目の誤入力でゲームオーバー
- 後半ほど難しい語を抽選

### CPU戦

- 30秒、10語の両方に対応
- CPU Lv1〜5
- 同じ問題番号では、プレイヤーとCPUに同じ3語を表示
- 攻撃なし。最終スコアを第一基準として勝敗判定
- CPUは読みの正答率、入力速度、ミス率、語句選択、キー管理、再抽選判断がLvにより変化

CPU戦は単なる追加モードではなく、将来のオンライン対戦に必要な共通問題列、相手状態表示、勝敗判定の検証環境として扱う。

## 4. 対戦の共通仕様

### 4.1 問題同期

対戦開始時に以下を確定する。

- ルームIDまたは対戦ID
- 乱数シード
- 辞書バージョン
- ゲームルールバージョン
- モード
- 難易度
- 開始時刻

各クライアントは同じシードから、問題番号ごとの3語を生成する。高速なプレイヤーと低速なプレイヤーは異なる問題番号へ進むが、同じ問題番号で表示される語句は共通とする。

再抽選用の3語も、問題番号とシードから決定する。再抽選を使うかどうかは各プレイヤーが個別に選ぶ。

### 4.2 同期する情報

リアルタイム同期は次の軽量情報に限定する。

- スコア
- 正解数
- HP
- ミス数
- 破損回数
- キー状態
- 復活待ち時間
- 入力中、待機中、終了済みなどの状態

相手の入力文字列や、先行プレイヤーが見ている次の問題は表示しない。配信画面では相手のミニキーボードと進行状況を主役にする。

### 4.3 遅延への対応

ゲーム進行は各クライアントで継続し、相手表示のみ通信結果で更新する。通信遅延で本人の入力やタイマーを止めない。

最終順位は、サーバーで検証されたスコア、正解数、破損回数、完走タイムなどで確定する。瞬間的な画面表示の遅延は勝敗に影響させない。

### 4.4 順位判定

第一基準は最終スコア。

同点時は原則として次の順で比較する。

1. 正解数が多い
2. 破損回数が少ない
3. 10語モードでは完走タイムが短い
4. ミスが少ない
5. 完全同一なら引き分け

10語モードのタイムボーナスはスコアに含まれるが、結果画面では完走タイムも独立表示する。

## 5. オンライン対戦ロードマップ

### Phase 0 — CPU戦

- 1 VS 1
- 共通シード問題
- 相手ミニキーボード
- Lv別の行動モデル
- 勝敗結果とSNS共有

### Phase 1 — ローカル・ゴースト戦

- 自分の過去プレイログをCPUの代わりに再生
- サーバーなしで相手表示の見やすさを検証
- 同じシードで自分の改善を比較

### Phase 2 — フレンドコード戦

- 2〜8人
- アカウント不要
- ルーム作成、短い参加コード、準備完了、再戦
- 自由チャットなし
- 表示名は自動生成名を初期値とする
- カジュアル版ではクライアント結果＋操作ログの終了時検証

### Phase 3 — 配信者向けルーム

- ルームURLまたはコード表示
- 参加人数、観戦表示、連戦設定
- 配信画面で読める小窓レイアウト
- 観戦者からのゲーム介入なし
- 先行問題や入力内容を隠し、答えの流出を防ぐ

### Phase 4 — 公開マッチング

- モード、難易度、人数帯で待機列を分ける
- 2人以上で一定時間後に開始し、最大8人まで参加
- 通報、ブロック、名前フィルター
- 操作ログのサーバー再計算
- 切断、復帰、放置の扱いを明文化

### Phase 5 — 公式ランキング

- サーバー完全検証
- 辞書・ルールバージョン別のランキング
- シーズン制
- 不自然な入力速度、改変クライアント、ログ欠損の除外

## 6. サーバー構成方針

ゲーム本体は引き続き静的ホスティングを維持する。対戦部分だけを別サービスへ分離する。

想定構成:

- GitHub Pages等: HTML、CSS、JavaScript、辞書
- WebSocketルーム: 参加者管理、開始時刻、状態配信
- ルーム単位ストレージ: シード、設定、操作ログ、結果

候補技術はCloudflare Workers + Durable Objects、または同等のWebSocket対応サービス。無料枠は変更され得るため、導入時点で料金・制限を再確認する。

WebRTCのみで最大8人を接続する構成は、シグナリング、切断復帰、ホスト依存が複雑になるため初期案では採用しない。

## 7. 不正・荒らし対策

公開マッチでは、クライアントから送信された最終スコアだけを信用しない。

記録対象:

- キー入力
- Backspace
- Enter判定
- 再抽選
- タイムスタンプ
- 定期チェックポイント

サーバーは操作ログから以下を再計算する。

- 正答判定
- 入力文字数ボーナス
- キー摩耗と回復
- 破損中キーの使用可否
- HP
- スコア
- クリアタイム

フレンド限定の初期版では検証を軽くしてもよいが、公開マッチと公式ランキングではサーバー再計算を必須とする。

## 8. CPU Lv方針

CPUの強さは単純な入力速度だけで変えない。

| 項目 | Lvが上がると |
|---|---|
| 読み知識 | 難しい語を正解しやすくなる |
| 入力速度 | 速くなる |
| 正確性 | タイプミスが減る |
| 語句選択 | 危険キーを避けやすくなる |
| 表記選択 | 長文得点と摩耗リスクを比較する |
| 再抽選 | 詰みや長い待機を判断して使う |

CPUは人間には不可能な完全情報を使わない。漢字の読みに失敗し、ミスし、キーを壊し、待機する余地を残す。

## 9. 今後のゲーム調整

優先して収集・検証する指標:

- 難易度別の正答率
- 各キーの使用率と破損率
- 最初の破損が起きる平均問題数
- 3語すべてが入力不能になる頻度
- 待機時間
- 再抽選使用タイミング
- `si / shi`等の表記選択率
- 長文入力が得点に対して過剰に有利になっていないか
- CPU Lv別の勝率

CPU Lvは、各難易度でLv1からLv5まで勝率が段階的になるよう実測で調整する。目安として、同程度のプレイヤーに対しLv3が約50%前後になることを目指すが、固定値ではなくプレイテストを優先する。

## 10. 語彙と法務

- 語句と読みは独自に選定・分類する
- 漢検公式問題や教材の問題配列、説明文、画像を転載しない
- 難易度はゲーム独自の目安と明記する
- 「漢検公式」「公式対応」など、提携を誤認させる表現を避ける
- 辞書更新時は辞書バージョンを変更し、対戦ログへ保存する

## 11. リリース運用

変更は次の種類に分ける。

- パッチ: バグ修正、文言修正、軽微な調整
- マイナー: 新モード、対戦機能、画面追加
- メジャー: スコア計算やキー摩耗ルールなど中核ルールの変更

リリース前に最低限確認する項目:

- JavaScript構文
- 全収録読みの正答判定
- 30秒、10語、CPU戦の終了条件
- 10秒復活
- 5ハート制
- 同一シードの問題一致
- CPU Lv1〜5が停止せず動く
- 画面幅ごとのレイアウト
- SNS共有の文面と画像
- 既存localStorage記録の互換性

差し替えZIPを作る場合は、変更ファイルだけを格納し、リポジトリ直下へ上書きできる階層を維持する。
